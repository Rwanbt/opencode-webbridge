# G23 — Empêcher le remplacement d'une action pendant son autorisation

La frontière G8 transforme une proposition d'outil issue d'un contenu web non fiable en données structurées, puis laisse OpenCode décider de l'autorisation. Un test adversarial a révélé que la proposition **mutable** d'origine était transmise à la fois au callback d'autorisation et au callback d'exécution. Une modification du nom d'outil ou des arguments durant l'attente asynchrone pouvait donc faire exécuter une autre action que celle approuvée ; l'ancien chemin transformait ensuite l'échec en effet « incertain », mais **après** appel au pilote. RED reproduit dans le test G23.

Le parseur refuse désormais les champs cachés/non énumérables, symboles et accesseurs sur les enveloppes et arguments. Il construit une copie JSON détachée, bornée à 16 K caractères, et récursivement gelée. La vérification du schéma, la demande de permission et le callback d'exécution utilisent **strictement la même copie immuable** ; une mutation de l'objet d'origine n'a aucun effet sur le contenu autorisé. Le scope d'agent/session/worktree est également copié et figé à la construction de la passerelle. Les tests démontrent le refus de getters, champs dissimulés et injection par mutation durant le grant.

**Limites :** ce correctif prévient une classe de confused-deputy/TOCTOU **au sein de WebBridge**, mais le callback `nativeAuthorize` fourni au contrat n'est pas encore une primitive d'autorisation transactionnelle officielle OpenCode. La consommation atomique des permissions par le broker/driver Desktop, la validation des schémas d'outils au point d'effet, les sous-agents et les opérations Git réelles demeurent à prouver sur l'application native. Une sortie web n'est jamais elle-même une approbation.

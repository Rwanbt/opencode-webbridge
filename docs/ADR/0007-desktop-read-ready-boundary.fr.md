# ADR 0007 — Vérification juste avant la lecture Chromium après `page.ready`

**Décision :** sur OpenCode V2 épinglé `4617210822bdbb31e5749751afbfb4584ccedac8`, la GUI Desktop refuse les commandes snapshot sans ticket `read.commit`, puis transmet sa sonde locale `liveRead` au dispatch. Après la réponse Core de commit, le driver peut attendre `page.ready`. La lecture ne doit donc pas partir si l'onglet a été remplacé, si la connexion est annulée, si la fenêtre/attachment a changé durant cette attente.

**Contre-exemple à l'ancien chemin :** `pane.execute` vérifiait l'attachement avant `read.commit` puis `await page.ready`, sans contrôle additionnel juste avant `page.execute`. La génération de l'onglet ou l'annulation pouvait changer pendant cet `await`. Le contrôle G56 `startCommittedRead` attend la même promesse, réévalue `liveRead` et invoque le driver sans autre suspension JavaScript entre test et appel. Test avec promesse `ready` différée : invalidation pendant l'attente signifie **zéro invocation du driver**. Un cas positif vérifie une seule invocation après chargement. Ce sont des tests dynamiques du helper appelé par `pane.ts`, **pas** un E2E Electron GUI/Chromium complet.

**Limites :** `liveRead` vérifie seulement l'attachement, l'annulation, la fenêtre et génération d'onglet locales ; elle n'observe pas instantanément toutes les mutations de politique Core dans un autre processus. Une révocation Core après `read.commit` et avant effet peut encore courir, ou le driver peut attendre de nouveau après l'appel. Le callback Core reste nécessaire au commit et au retour du résultat, mais cela ne crée **aucune transaction atomique Core/GUI**. Une autorité sérialisée commune au host/driver, avec reçu durable et tests de révocation pilotant la vraie primitive Chromium, demeure obligatoire avant certification. Pas d'écriture native `navigate/click/fill/submit` par cette API, pas de fournisseur commercial actif, pas de merge ni de modification upstream distant ou Unifia.

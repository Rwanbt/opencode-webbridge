## Preuves conjointes sur **un même SHA de PR** (pas le même processus)

- **Job `upstream-v2-browser-patch` :** une copie temporaire du **vrai code source officiel** épinglé reçoit le patch complet et exécute le typecheck des packages plugin, plugin-browser, core et GUI, puis la suite native `read-commit.test.ts`, `first-attach-authority`, `connection-location`, `attach-ownership`, `tunnel-provenance`, `browser-one-shot`, politique, registre RPC et gate GUI. Les scénarios RED (code G126) → GREEN (patch G131) sont les notifications `tab(1)→tab(2)→tab(1)` avant `read.commit` et après `read.live`, ainsi que l'URL changée sans incrément de génération. Les snapshots de `browser.tabs.list` restent liés aux règles Core et à l'attachement de **fixture** autorisé.
- **Job `g130-official-v2032-durable-read-receipts` :** sur le **même commit WebBridge**, installe un exemplaire public exact de `@opencode/cli@2.0.32`, **un** plugin `.tgz` produit localement, une page Chromium localhost, et exécute réellement DOM→RPC→fragments→sink chiffré du **host de test** (`fsync` avant SSE)→SSE→CLI. Le host réconcilie les ACK perdus après écriture, rejette réémissions conflictuelles et mauvaises portées, persiste le reçu au redémarrage du sink et recoupe l'historique de session obtenu après redémarrage réel du **serveur CLI**. Le job commence également par le contrôle octet-identique du patch G131. Les deux scénarios `tab-change` et `browser-disconnect` restent actifs.
- Les jobs G125, 2.0.29 et Windows restent inchangés. Ces preuves démontrent **la coexistence dans une unique révision WebBridge**, **pas** l'exécution du patch Core dans le processus `@opencode/cli@2.0.32` installé (ce binaire est stock, jamais recompilé). Les snapshots locaux et les host receipts n'attestent ni Electron ni l'autorité `read.commit` native sur le CLI installé.

## Contrat de blocage

**G132 qualification CI G125 après revue des deux runs initiaux :** le push du premier SHA `dd8eed7460ec895c8bfb63dd762f67de67b4fd4a` a échoué sur une observation ponctuelle de `/api/session/{id}/message` immédiatement après la sortie CLI, alors que le run PR du même SHA réussissait. Un `finish:'stop'` assorti du contenu exact n'était pas encore visible dans cette réponse initiale : cela **ne démontre pas** qu'il était définitivement absent, ni que le run PR suffit à qualifier le push. Le lecteur durable effectue désormais au plus 20 relectures espacées de 100 ms **uniquement** pour le résultat final positif attendu ; il ne remplace jamais la condition stricte `finish === 'stop'` et contenu exact par le SSE ou la sortie CLI. S'il manque toujours, **échec explicite**. Après redémarrage effectif du serveur CLI, le lecteur utilise séparément son ancienne boucle bornée (75 observations à 200 ms), sans attente imbriquée, et exige encore le même contenu exact. Tests RED→GREEN de l'API HTTP officielle simulée : commit final apparaissant au troisième GET, absence définitive, faux terminal, faux texte, et interruption ne pouvant se déclarer terminée. Les jobs G125 **et** G130 exécutent cette régression. Cela traite le problème d'observation de persistance de fixture sans affaiblir la preuve ; un défaut de durabilité réelle demeure NO-GO.

Le Core natif V2 conserve `BrowserConnection.make(ctx)` sans vérificateur OS : le **premier attachement Desktop reste fail-closed**. L'identité du processus Electron Main ne traverse pas le HTTP RPC vers le Core. Les fixtures `verify: () => true` ne sont pas des attestations OS. Les fenêtres revocation→Chromium effect ne sont pas atomiques entre processus. Pas d'activation de compte ou fournisseur commercial (**0/5**), pas d'écriture navigateur (**OFF, 0**), pas de pilote E5 dans ce lot. La proposition n'est pas un E2E d'un Core corrigé dans le CLI officiel ni une preuve de Desktop empaqueté ; **NO-GO production**, pas de merge avant les contrats système et leurs tests réels.

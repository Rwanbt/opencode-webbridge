# ADR 0005 — Refus des snapshots non attestés (suivi E2 de #118)

**Statut : correctif de référence, lecture seule, non certifié.** Le patch s'applique à OpenCode officiel V2 `4617210822bdbb31e5749751afbfb4584ccedac8` et ne modifie pas l'upstream ni Unifia. Aucun `navigate`, `click`, `fill`, `submit` ou autre effet d'écriture n'est activé.

**Contre-exemples RED sur #118 :** `PluginBrowser.snapshotOnce` pouvait exécuter `bound.read()` avec seulement quatre `permission.assert` successifs, **sans** appeler `Permission.Service.browserRead` ni consommer son epoch. L'ancien `ctx.browser.snapshot` lisait avec la seule permission générale. `BrowserConnection.target(...snapshot).request([])` — chemin utilisé également par le tool `browser.snapshot` de Code Mode — envoyait une commande RPC **sans** `read.commit`, que le Desktop exécutait puisque son garde ne s'appliquait que si `readCommit` était présent. Les tests négatifs reproduisent une lecture non autorisée et une commande RPC envoyée.

**GREEN :** `snapshotOnce` refuse si le service Core `browserRead` est absent. La vraie instance `Permission.Service.browserRead` émet maintenant la décision scoped à l'agent attesté par `BrowserTurn`, la session, l'espace, le message, l'appel, l'ID de plugin et une génération aléatoire créée par Core lors de l'activation, la connexion Desktop, l'onglet/génération et l'action exacte `snapshot.once`. Le broker consomme cette décision synchroniquement juste avant d'invoquer `bound.read()`, sans `await` entre consume et dispatch. `BrowserTurn.valid` compare aussi l'agent initial. Les deux API héritées `ctx.browser.snapshot` et `BrowserConnection.target.request(snapshot)` refusent désormais ; seule la voie `requestOnce` du builtin peut transmettre ce snapshot avec le commit Desktop de #118. Tests RED→GREEN et intégration réelle `Permission.Service` prouvent qu'une révocation d'epoch entre issue et effet empêche la lecture.

**Ce n'est PAS une autorité Desktop atomique complète.** Une fois consommée côté Core, la permission peut être révoquée avant le RPC `read.commit` ou avant l'observation de la page. Il manque un commit sérialisé entre l'autorité Core et le moteur Desktop, une provenance protégée contre le code malveillant exécuté dans le même processus et des reçus durables lors d'issues incertaines. Le builtin peut toujours invoquer directement son `requestOnce` interne, mais cette fonction n'est pas exposée aux plugins tiers ; cette hypothèse de confiance doit être revue. Les autres tools navigateur historiques (`frames`, réseaux, captures, etc.) **ne sont pas tous couverts** et conservent leurs contrôles historiques. Les mutations hors API de permissions peuvent échapper aux révisions ; **les corrections de hooks/consentement de #120 et des suivis worker-3 sont des prérequis d'intégration**, non inclus dans cette branche. Les snapshots hérités cessent temporairement de fonctionner plutôt que contourner l'autorité. Aucune certification de lecture générale, aucun site tiers, aucun compte réel.

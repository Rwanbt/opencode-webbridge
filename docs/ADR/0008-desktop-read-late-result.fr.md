# ADR 0008 — Refus du résultat de snapshot après révocation locale

**Contexte.** Dans le patch OpenCode V2 épinglé `4617210822bdbb31e5749751afbfb4584ccedac8`, le helper natif `startCommittedRead` (G56) attendait `page.ready`, testait `liveRead`, puis renvoyait la promesse `page.execute`. Si l'attachement Desktop, la connexion, l'onglet ou sa génération était invalidé **pendant** l'exécution asynchrone du driver, le résultat pouvait encore être propagé à l'appelant malgré la révocation locale.

**Décision.** Attendre le résultat du driver et recontrôler synchroniquement `liveRead()` avant de le retourner. Si la liaison n'est plus valide, lever une erreur générique et ne jamais propager le contenu du snapshot. Le contrôle antérieur à l'effet est conservé. Le résultat de l'opération ne peut pas être rejoué en cas d'échec ou de statut incertain.

**Test adversarial RED → GREEN.** Sur le vrai module TypeScript du patch épinglé, le test retarde la promesse du driver, vérifie que le driver a été appelé une fois, invalide le binding pendant l'attente, puis résout cette promesse avec un marqueur de contenu privé. **RED initial :** `AssertionError: Missing expected rejection.` **GREEN :** `GREEN: revoked Chromium read never returns secret content`. Une régression Bun native est ajoutée dans `read-commit-gate.test.ts`. La génération du patch unique a été contrôlée par `git apply --check`, application, puis `git apply --reverse --check` sur un nouveau checkout officiel isolé.

**Limites / NO-GO.** Cette mitigation empêche l'exposition du résultat **à cette frontière GUI seulement**. La lecture Chromium a potentiellement déjà eu lieu ; le contenu peut exister dans le driver et le délai entre le second contrôle et d'autres traitements IPC n'est pas une transaction atomique. La révocation de politique **Core** n'est toujours pas observable instantanément dans le processus GUI ; aucune preuve d'atomicité Core ↔ Desktop ↔ effet réel n'existe. Aucun E2E Electron GUI n'est revendiqué. Les opérations `navigate`, `click`, `fill` et `submit` restent désactivées pour WebBridge ; les cinq fournisseurs commerciaux restent inactifs et aucune PR n'est fusionnée.

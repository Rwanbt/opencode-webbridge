# ADR 0127 — G174 : vrai binaire Desktop 2.0.32 introuvable, plugin serveur installable

**Base exclusive :** intégration G173 #252 SHA `b2dadd94cf2d6e980c38edb385124fccad57ca29`, nouveau worktree séparé. Les CI de base push `39088507393` et PR `39088511291` ont toutes deux échoué ; ne jamais les qualifier de vertes.

**Observation reproductible (18 octobre 2026) :** le tag officiel `anomalyco/opencode refs/tags/v2.0.32` existe et résout `843a6c514e606b436a7fe713422ace0a93ad3d61`. `GET /repos/anomalyco/opencode/releases/tags/v2.0.32` retourne HTTP **404**, donc il n'existe pas de binaire Desktop 2.0.32 téléchargeable via **cette distribution GitHub**. `npm view @opencode/desktop@2.0.32` retourne E404 ; `@opencode/cli@2.0.32`, lui, est disponible. Le `latest` public possède bien des binaires Desktop mais sous **v1.19.3**, pas v2.0.32 : ne pas mélanger les versions ni attribuer à un binaire v1.x des propriétés du source v2.0.32. L'absence ne prouve pas qu'aucun binaire privé/nouveau canal de distribution n'existe.

**Preuve exécutable, distincte de toute émulation Electron :** `scripts/g174-desktop-artifact.mjs` interroge chaque fois le tag et la release publics, contrôle provenance, noms, tailles et SHA-256 des éventuels futurs assets ; tout 403/401 est **indéterminé**, jamais interprété comme absent. Si un binaire officiel v2.0.32 apparaît, ce test refuse de prétendre le Desktop validé et exige son exécution réelle dans un profil jetable. Il réutilise `loadOfficial/proveOfficialPublicApi` du dépôt, vérifie le SHA256 intégral des **quatre sources publiques officielles gelées** et exécute en VM uniquement leur handler `ExtensionInstall`/enable/reload : avec `app.isPackaged=true`, il renvoie `unavailable` avant tout effet host. Un test contre-factuel enlève cette condition dans la VM et montre que la demande d'installation atteint le host. Cette preuve est **sur du code Electron transpilé**, pas sur un vrai processus Electron.

**Produit réellement exécutable aujourd'hui :** `scripts/g174-native-plugin-install.mjs` construit le `npm pack` **brut** du véritable plugin WebBridge, l'installe avec `npm install <archive> --prefix <temp>`, puis démarre uniquement le CLI officiel 2.0.32 dans des répertoires HOME/XDG et configuration isolés. Il exige l'entrypoint packagé réel, le plugin `opencode.webbridge` en état `active` via `/api/plugin`, la lecture de `/api/provider` et `/api/config`, et l'absence des cinq modèles commerciaux non prouvés. Ni staging artificiel, ni compilation, remplacement ou lancement de l'installation OpenCode de l'utilisateur. L'activation CDP y est limitée à un port local déclaré mais aucun navigateur personnel n'est connecté. **Cette validation serveur CLI ne démontre pas le sélecteur GUI Desktop.**

**Proposition minimale en amont, SANS édition upstream :** conditionner le refus `ExtensionInstall` empaqueté à une vérification d'autorité explicitement OS/IPC-trusted plutôt qu'à un blocage global ; fournir dans l'installateur Desktop un parcours signé/consenti d'installation de bundles tiers, activation, provenance, révocation, rollback et découverte de contributions renderer déclaratives. Conserver la séparation plugin serveur `provider.transform`/tools et extensions GUI Electron, sans inventer `renderer` dans le SDK de plugin serveur. Avant toute acceptation : obtenir un **artefact Desktop 2.0.32 authentique**, confirmer hash/source, lancer en profil temporaire sans compte, installer l'extension tierce signée, voir contributions et sélecteur GUI réellement actifs puis les retirer. Aucun patch d'application officielle ni de dépôt distant n'a été appliqué.

**Verdict :** chargement externe via CLI 2.0.32 prouvable, **Desktop empaqueté 2.0.32 NO-GO (artefact indisponible, IPC GUI externe refusé dans la source)**. Aucune attestation OS/Electron effective, pas de garantie 5/5 fournisseurs, modèles commerciaux `0/5`, acceptation `0/54`, écritures navigateur OFF et production NO-GO.

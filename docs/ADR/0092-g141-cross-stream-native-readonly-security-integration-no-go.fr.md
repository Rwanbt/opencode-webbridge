## Limites et NO-GO

**Ces capacités coexistent sur le même commit WebBridge ; elles ne tournent PAS dans le même processus Core patché.** Le processus du CLI officiel distribué est distinct du checkout Core natif temporairement patché dans une autre tâche CI. Ni ce CI, ni un token HTTP, ni la présence d'un hôte de fixture ne prouvent une attestation OS de l'IPC Desktop/Electron, une autorité de navigateur native, un consentement utilisateur effectif ou une transaction atomique Core ↔ Chromium. Le parseur G138 valide des données sérialisées, non la provenance authentifiée des octets ; le broker G139/G140, la quota G142 et l'exécuteur G135 restent des contrats/fixtures, sans exécution native Core autorisée. Sous Windows, `file.read` refuse faute de confinement OS sûr ; la fixture Git hostile n'est pas un sandbox OS. La reprise post-panne d'un effet navigateur n'est pas garantie atomique. **0/5 fournisseurs commerciaux, 0 acceptation de production, 0 écritures navigateur (OFF)** ; premier attach Desktop bloqué sans provenance OS fiable. Aucun code provider E5/G134 et aucun binaire officiel n'est modifié.

Une véritable sortie de NO-GO exigerait un broker de capacités et permissions intégré au Core distribué, une identité de processus Desktop attestée, un confinement OS des handles et effets, des reçus applicatifs anti-rejeu, un contrôle de divulgation et les tests live Electron + Core patché **dans le même processus effectif** avec consentement explicite.

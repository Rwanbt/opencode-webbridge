# ADR-0002 — Browser capability boundary for OpenCode v2 plugins

Status: **PROTOTYPE ONLY** · 2026-10-17 · base: `feat/g7-operator-reconciliation` (`74ce1d4`)

## Evidence and scope

- Installed `@opencode/plugin@2.0.29` exposes `rpc` and `permission` but **no `browser`** on `Plugin.Context`: `node_modules/@opencode/plugin/dist/promise/plugin.d.ts`. The TUI's separate `dist/tui/context.d.ts` exposes routes, panels and rendering; it contains no direct browser control surface. Type assertions in `test/browser-host-capability.test.ts` fail to compile if those fields change unexpectedly.
- `ctx.rpc.register` registers typed **plugin RPC**: `dist/promise/rpc.d.ts`. It does not install an embedded-browser driver. `ctx.permission.assert` is available: `dist/promise/permission.d.ts`.
- The [official V2 tools documentation](https://dev.opencode.ai/v2/docs/tools/) describes the agent-facing `browser` namespace on a browser attached to **OpenCode Desktop**, scoped by explicit `tabID`. A `browser` deny rule removes that catalog; browser calls have no per-operation prompt. No publicly documented direct `ctx.browser` plugin extension was found in [server plugins](https://dev.opencode.ai/v2/docs/build/plugins/) or [CLI plugins](https://dev.opencode.ai/v2/docs/build/plugins/cli).
- Actual upstream **`v2` source** at [`4617210`](https://github.com/anomalyco/opencode/tree/4617210822bdbb31e5749751afbfb4584ccedac8) **does provide a built-in browser integration**: `packages/plugin-browser/src/index.ts` registers a first-party `opencode.browser` plugin; `src/tools.ts` registers the `browser` Code Mode namespace with `options.permission: "browser"`, and `src/rpc.ts` defines its Desktop RPC. [`packages/plugin-browser/README.md`](https://github.com/anomalyco/opencode/blob/v2/packages/plugin-browser/README.md) explicitly scopes this to Code Mode. This existing browser is **not** a public `ctx.browser` API for arbitrary server plugins.
- The native GUI extension lives at `packages/gui-extensions/src/browser`. Its `contract.ts` only publishes `attached`, `canOpen`, `open`, `openFile` (view/pane navigation); it does not expose DOM or chat-turn automation. [`packages/gui-extensions/README.md`](https://github.com/anomalyco/opencode/blob/v2/packages/gui-extensions/README.md) describes typed `Extension.define` / `ctx.provide` / `ctx.add` composition. `src/renderer.ts` statically composes the built-in extensions. No third-party package loading path into that host was established.
- `D:/App/OpenCode/opencode` is a local **Unifia/V1 fork**, and `D:/App/opencode-src` is an older official V1 checkout (2026-08-17). Neither constitutes the installed V2.0.29 Desktop browser source. These facts establish the public SDK contract, not the absence of undisclosed internals.

## Decision and proposed upstream capability

An upstream enhancement should expose a **supported, host-mediated browser capability** from the existing first-party browser integration to explicitly authorized server plugins. It needs lifecycle registration, host-held tab ownership, granular permission rules, and a user-controlled consent grant. It must specify which desktop instance owns each tab and how disconnection/revocation invalidates claims. Propose an official plugin domain or host-approved adapter; directly calling the first-party browser's internal RPC is not a supported integration surface and could bypass the existing tool permission model.

The optional `BrowserHostCapability` prototype wraps the existing `BrowserPort` and fails closed if no host has registered. Before claiming and before each submit/read, it checks host consent, `ctx.permission.assert` for the built-in `browser` action (`*` resource), and a separate `webbridge_browser` action scoped to `providerID:tabID`. It rejects ownership mismatch and duplicate registration. Cancellation and release remain possible after revocation to avoid retaining a stale claim. The host controls how consent is collected; the plugin must never mint its own authorization or expose cookies, tokens, DOM, or account credentials.

This **does not** install a new OpenCode browser extension, register provider models, or authorize real web-chat accounts. The only tested driver is `FakeBrowserPort` offline. Real integration still requires a publicly supported adapter to the existing V2 browser, verifiable consent provenance (the injected `consented` callback alone is no security proof), atomic host-side revocation enforcement, permission semantics validation in the actual V2 runtime, and provider policy approval before changing the default `ProviderGate` state.

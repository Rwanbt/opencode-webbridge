# ADR 0045 — Provenance du RPC browser et attestation OS : NO-GO

**Statut :** patch de sécurité amont proposé pour `anomalyco/opencode@4617210822bdbb31e5749751afbfb4584ccedac8`, empilé sur G121 PR #199. **Ne pas fusionner pour la production.** Aucune attestation native du processus Desktop n'existe encore dans le Core épinglé ; `experimental.browser.attach` reste interdit sans `DesktopAttachAuthority` fiable. Écritures WebBridge désactivées, fournisseur commercial validé : **0/5**.

## Preuve négative sur les chemins exécutables réels

1. `packages/desktop/src/main/ipc.ts` établit un `MessageChannelMain` depuis une vraie `BrowserWindow`; `ipc-transport.ts` conserve `WebContents` (sender ID) et débranche le port à sa destruction. **Cette identité n'existe que dans le processus Electron**, pour les RPC de l'interface à Electron Main.
2. `packages/desktop/src/main/service/background-service.ts` peut **réutiliser** un service CLI externe déjà découvert et communique par URL HTTP avec authentification **Basic**. `packages/gui-extensions/src/browser/pane.ts` appelle `OpenCode.make({baseUrl: server.url})`, puis `client.rpc(Browser.Definition)` : aucune connexion IPC OS avec identité du processus Desktop ne traverse cet appel.
3. La route HTTP `packages/server/src/handlers/rpc.ts` invoque `Rpc.Service.call(rpcID, method, input)` sans identité de l'appelant. `packages/core/src/rpc.ts` fournit au handler le seul `callContext = { error }`. `RpcCallContext` de `packages/plugin/src/effect/rpc.ts` expose uniquement `error`. Test natif exécutable `browser-rpc-provenance.test.ts` : même une requête contenant des champs forgés `peerPID`, `claimedElectron` et `verified` n'apporte **aucun** principal OS au handler. Les UUID V6 et le Basic bearer ne prouvent donc pas Electron.

## Nouveau contournement réellement démontré (et corrigé)

Le Core expose `ctx.rpc.register` **à chaque plugin**, y compris ceux chargés depuis une source utilisateur ; `Rpc.Service.call` sélectionne le **dernier** handler d'un nom RPC (`.at(-1)`). Sur G121, un plugin externe déclaré `opencode.browser`, même avec métadonnées d'origine falsifiées, pouvait enregistrer son **propre** `experimental.browser.attach` et répondre `closed` sans passer par la porte `BrowserConnection.make` qui refuse le premier attachement. Il pouvait aussi falsifier les résultats `read.commit`/`read.live`. Test effectif **RED** sur le patch précédent : le registre malveillant s'active et remplace le handler ; il passe **GREEN** en G126.

Le Core définit maintenant un `rpcFor(pluginID, trustedBuiltin)` **non énumérable**, construit à chaque activation : seuls `pluginID === "opencode.browser"` **et** l'identité de fonction builtin enregistrée par le `WeakSet` privé de `PluginInternal` peuvent enregistrer `experimental.browser`. Le `source` déclaré par le plugin n'accorde aucune autorité. En complément, `Rpc.Service.register` refuse l'écrasement d'une inscription `experimental.browser` encore active, tandis que les autres RPC conservent leurs comportements préexistants. Un test adversarial réel couvre l'identifiant et `source` falsifiés, un autre couvre un deuxième enregistrement privilégié après le premier. Aucun accès au navigateur n'est rouvert ; le miroir Core `browser.tabs.list` reste disponible si, et seulement si, une attache indépendante réellement vérifiée existe.

## Contrat OS IPC nécessaire avant toute mise en service

**Nouvelle frontière obligatoire** : le Core héberge un point d'entrée IPC natif exclusif pour l'enregistrement Desktop, **distinct** de l'API HTTP/RPC et indisponible sur les interfaces réseau. Une primitive OS fournie par le noyau doit exposer au **serveur Core**, et jamais au client sous forme de champ JSON ou de header, un `VerifiedDesktopPeer` : identité du processus et de l'utilisateur/session OS, instant de création ou handle stable non réutilisable, canal opaque lié au processus, provenance de l'exécutable Electron signé/vérifié selon la politique de plateforme, identité de l'instance du serveur, et signal de fermeture/revocation.

Implémentations à spécifier et auditer indépendamment : Windows **named pipe** créé par le Core avec DACL restrictive, identification kernel du pair via `GetNamedPipeClientProcessId` et vérification du jeton/processus et de l'exécutable ; Linux **AF_UNIX / SO_PEERCRED** avec vérification de l'identité du processus et du binaire ; macOS socket UNIX avec `getpeereid` et mécanisme OS permettant une vérification de PID + signature du code. UID/SID, PID, chemin, parent PID ou numéro de port seuls sont **insuffisants** : un autre programme du même compte peut les partager/usurper indirectement. Les garanties de signature et d'identité doivent être qualifiées par OS et compte utilisateur, ainsi que le risque d'un processus déjà compromis.

Le transport doit fournir au **Core**, hors des champs contrôlés par le client, un handle de pair non exportable et son canal actif. La future `RpcCallContext` côté handler privilégié doit exposer un type discriminé `VerifiedDesktopPeer` produit exclusivement par l'adaptateur IPC Core ; une requête HTTP ne peut pas le construire. `DesktopAttachAuthority.verify` doit confirmer ce canal vivant, l'identité app/signature attendue, l'instance Core, les `sessionID` et workspace issus de la base Core, la connexion et la génération de l'attache ; elle doit révoquer attache/permission/lectures/tunnels immédiatement à la fermeture ou ré-identification du canal. Le Desktop doit initier ce canal à travers Electron Main, non le renderer ni une interface web.

**Tests bloquants pour lever le NO-GO :** processus autre que Desktop, même utilisateur et même Basic bearer ; client TCP distant ; UUID et header auto-signés ; faux nom ou source de plugin ; réutilisation d'un PID/pipe fermé ; service CLI réutilisé ; tab/session déplacée ; résiliation de l'IPC pendant un prompt ou un `read.live` ; faux exécutable sous chemin similaire ; vrai Desktop avec la signature validée et les permissions Core requises. Aucune fixture `verify: () => true` ne vaut attestation. Les effets Chromium et commits inter-processus exigent une qualification séparée.

**Décision :** les mécanismes OS et la migration IPC/HTTP n'existent pas dans le commit officiel épinglé. Les implémenter dans ce seul lot en moins de 400 lignes et sans exécution Electron réelle serait une fausse garantie. G126 protège **réellement** contre l'usurpation de l'inscription RPC et fournit la preuve négative exécutable, mais conserve **NO-GO première attache, Desktop packagé, fournisseurs commerciaux et production**.

# ADR 0089 — G138 : frontière JSON sérialisée pour propositions d'outils non fiables

**Statut : fixture de validation, NO-GO autorité native / production.** Base exclusive : PR #213 G136, `41bfbf02244050374d4c4555ccdfd626cfe51c10`. Ce lot ajoute seulement `src/core/tool-proposal-json-ingress.ts`, son test indépendant et cette ADR. Aucune modification de `tool-proposal.ts` (G133), des brokers G136, du natif/CI G132/G137, de l'exécuteur G135 ou des adaptateurs E5 G134.

## Contrat à la frontière de processus

`ingestToolProposalJSON(wire, hostScope)` accepte seulement une **chaîne primitive** ou des octets authentiques `Uint8Array`/`Buffer` ; ni objet de proposition JS, ni `String` objet, ni proxy de tableau typé. Le contrôle des octets utilise les accesseurs et méthodes **intrinsèques** des tableaux typés puis réalise une copie avant décodage UTF‑8 `fatal`, sans accès aux propriétés applicatives, `toJSON`, getters ou pièges de `Proxy`. `hostScope` est fourni séparément par le processus hôte de confiance ; aucune identité, permission ou grant n'est inférée du web/modèle.

Avant `JSON.parse`, un scanner déterministe vérifie **un seul document** RFC 8259 (pas de BOM, commentaire, document concaténé ni caractères bruts interdits), au plus **16 KiB de données UTF‑8**, **256 jetons**, **12 niveaux de conteneurs**, **8 192 unités UTF‑16 par chaîne**. Les clés sont décodées **avant comparaison des doublons**, notamment les alias `\u0061ction` ; les clés `__proto__`, `prototype`, `constructor` sont rejetées à toute profondeur, même échappées. Les chaînes sont vérifiées contre les paires de substituts UTF‑16 invalides, contrôles C0/C1, certains caractères de format directionnels et caractères non admissibles. Les chaînes JSON contenant des séquences de contrôle échappées dangereuses sont rejetées, comme les contrôles non échappés. Les valeurs JSON sont ensuite passées **une seule fois** à `validateToolProposal` G133 : seules les actions de lecture admissibles, les arguments plats et la provenance strictement égale au `hostScope` ressortent en objet **gelé et détaché**. Les refus sont gelés et ne reflètent jamais l'entrée potentiellement sensible.

## Scénarios RED→GREEN et limites

Le test introduit avant le module produisait RED (`TS2307` : module introuvable) ; une fois implémenté, les scénarios vérifient le roundtrip UTF‑8 (string, Buffer, Uint8Array), les doublons directs ou échappés à toute profondeur, les clés polluantes, les champs de commande cachés, la portée fausse, les actions mutables/inconnues, la syntaxe et les documents annexes, les `null`, les nombres malformés, les caractères de contrôle/bidi, les paires de substituts invalides, le décodage UTF‑8 invalide, les limites octets/jetons/profondeur, ainsi que l'absence d'invocation de getters, `toJSON` et pièges de Proxy de l'**entrée**. Ces tests sont découverts automatiquement par `npm test` dans le job Linux `checks`, sans altérer la CI appartenant à d'autres lots.

Les limites sont volontairement strictes : ce n'est **ni un canal IPC attesté**, ni une vérification cryptographique de l'émetteur, ni un broker de permissions/consentements, ni un outil exécutant une opération. Le processus hôte doit contrôler la provenance des octets, la source de `hostScope`, la gestion des interruptions et les droits de tout effet ultérieur. Le contrôle Unicode ne remplace pas une politique de texte complète ; les octets issus de mémoire partagée peuvent varier durant la capture, mais seule la **copie prise localement** est analysée. Un appelant qui a déjà converti des octets invalides en chaîne avec remplacement ne permet pas de reconstituer la validité originale de ces octets. Aucun effet navigateur, terminal, OS, réseau, fournisseur commercial, ou mutation n'est ajouté ; **0/5 fournisseurs, 0 acceptation, écritures navigateur OFF, NO-GO production**.

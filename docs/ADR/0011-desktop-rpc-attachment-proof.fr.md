# ADR 0011 — Séparer l'ID de routage public de la preuve d'attachement RPC

**Défaut.** Dans le protocole V5, `connectionID` servait simultanément de routage dans les événements `rpc.experimental.browser.control` diffusés par le flux serveur et de seule liaison pour les RPC `state`, `command`, `read.commit`, `read.live`, `result` et `tunnel.*`. Un autre client disposant déjà d'un accès API pouvait apprendre cet ID et tenter de modifier l'inventaire, de répondre à une requête ou d'ouvrir un tunnel TCP côté serveur. Cette analyse de chemins d'appel n'atteste pas une exploitation via un site web non privilégié.

**Décision.** Dans le patch du commit officiel `anomalyco/opencode@4617210822bdbb31e5749751afbfb4584ccedac8`, le protocole **V6** ajoute un `attachmentProof` aléatoire, indépendant de `connectionID`, créé dans le processus Desktop et transmis uniquement par les appels RPC attachement/état/commande/commit/résultat/tunnel ; aucun événement Control ne le divulgue. Le Core refuse ces appels en cas de preuve absente ou différente, en plus des contrôles de session/connexion préexistants. La reconnexion invalide la preuve précédente; les Desktop V5 ne peuvent plus joindre le serveur V6. Ce changement est strictement un mécanisme de possession d'une capacité éphémère, **pas une attestation cryptographique de processus**.

**Tests négatifs.** Le test hôte utilise deux capacités : l'identifiant de connexion public et une preuve fausse, contre une connexion avec une preuve privée. Il vérifie refus de `state`, `command`, `read.commit`, `read.live`, `result` et `tunnel.open`, même après connaissance du ticket de lecture valide, puis succès de la connexion légitime. Les schémas RPC rejettent les appels sans preuve et les Control V5 anciens. CI hébergée obligatoire pour les tests exécutables et vérification du patch épinglé.

**Limites critiques / NO-GO.** Un client API malveillant déjà autorisé peut encore tenter lui-même un **nouvel `attach`** et créer sa propre preuve : cet incrément n'authentifie ni l'identité Electron ni les droits à créer un attachement. Les requêtes RPC restent couvertes par les droits d'accès généraux du serveur et doivent recevoir une autorité liée à la session et au host au niveau transport pour clore la confusion inter-clients. Aucune preuve d'E2E Electron, d'atomicité de révocation Core↔Chromium, de reprise crash ni de journal durable pour ces effets. Les `tabs.list` historiques restent indisponibles depuis G58; les écritures WebBridge et les cinq adaptateurs commerciaux restent désactivés. Aucune fusion ni modification upstream.

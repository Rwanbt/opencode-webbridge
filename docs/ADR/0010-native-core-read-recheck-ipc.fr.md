# ADR 0010 — Réévaluation Core post-readiness et IPC local refusé pour les lectures

**Défauts.** Le commit de lecture `read.commit` pouvait réussir, puis le Desktop attendre `page.ready` tandis que la politique Core était révoquée. G56 vérifiait uniquement l'attachement **local** après l'attente : aucune nouvelle confirmation de Core n'intervenait avant `page.execute`. Une seconde entrée `browser.pane.command` provenant du renderer appelait directement `execute()` sans passer par le filtre G58 appliqué au RPC agent.

**Correctifs natifs ciblés.** Sur le commit officiel OpenCode V2 épinglé `4617210822bdbb31e5749751afbfb4584ccedac8`, `read.live` vérifie une lecture **déjà** consommée et committée, le ticket exact, la connexion, l'époque de permission Core, le délai et la génération d'onglet. Après `page.ready`, le Desktop appelle ce nouveau RPC; le moindre refus/échec empoisonne définitivement le commit et empêche l'effet Chromium, même si un callback simulé redevient autorisé. Le Desktop réévalue aussi son attachement local après cet `await`. Le protocole de connexion `experimental.browser` passe **de V4 à V5** : un Desktop ancien incapable d'appeler `read.live` est refusé, et ne peut contourner cette nouvelle étape. Le chemin renderer `browser.pane.command` refuse toute action hors de l'allowlist d'effets first-party G58 avant d'invoquer `execute`; un ticket `snapshot` ne lui est jamais transmis.

**RED → GREEN exécutable.** Un harness Bun importait le réel `startCommittedRead` source et simulait une révocation Core après `read.commit`, pendant un chargement différé. Avant correctif, `AssertionError: Missing expected rejection` et effet Chromium simulé initié; après, `GREEN: post-commit Core revocation prevents Chromium effect`, avec zéro effet. Nouveaux tests officiels : refus de `read.live` avant commit, après révocation, ticket usurpé, connexion différente et epoch non ressuscitable; refus de l'exécution après readiness / changement de Desktop pendant l'attente RPC; gate renderer pour snapshots, métadonnées, captures et commandes inconnues. Le chemin IPC est vérifié à la source et via sa fonction de contrôle, **pas par un E2E Electron réel**.

**NO-GO.** Ce protocole *réduit* la fenêtre de révocation distante mais n'assure **aucune sérialisation atomique** Core ↔ Desktop ↔ Chromium. Une révocation Core immédiatement **après** `read.live`, **avant** l'exécution Chromium, reste possible. Aucun effet déjà engagé n'est annulé ni certifié; le journal durable et la récupération crash/uncertain ne sont pas établis pour Desktop. La liste GUI héritée `tabs.list` reste volontairement bloquée et nuit à la compatibilité native. Aucun `navigate`, `click`, `fill`, `submit` WebBridge, aucun site fournisseur commercial, aucun compte/cookie récupéré. Interdit de proposer ce patch tel quel comme intégration upstream production-ready sans résolution de ces points et preuve Electron officielle.
